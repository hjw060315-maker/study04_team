# 구현 계획

PRD(`docs/PRD.md`)를 단계로 나눈다. 단계마다 연습용 시나리오로 확인하고 커밋한다. 하루 단위 일정은 마감(11/2)까지 약 11일을 기준으로 한 목표이다.

## 파일 구조
```
streamlit_app.py     화면(Streamlit), key 지정, 흐름 연결
src/db.py            연결 1회 생성·재사용, 질의 함수
src/rules.py         순수 규칙 함수(DB·화면 모르게): 역할 검사, 필수 역할 매칭, 지원 막힘 판정
src/service.py       지원·투표·승인·마감·확정 로직(트랜잭션)
src/assign.py        AI 호출(3단 폴백, 120초 제한), 배정안 검사, 완전 탐색 배정
src/auth.py          bcrypt 해시, 로그인, 관리자 계정 시드
schema.sql           tf_ 테이블 생성 SQL
tests/               rules, assign 단위 테스트, 부록 시나리오 테스트
docs/                PRD, 구현 계획
.env                 키(커밋 금지)
```
규칙과 배정 검사는 순수 함수로 두어 DB 없이 테스트한다. 같은 함수를 지원 단계, 승인 직전, AI 배정 검사, 직접 배정이 함께 쓰므로 규칙이 한 곳에만 있다.

## 단계

### 0단계: 준비 (사용자 직접)
- OpenRouter 키 발급과 모델 3개 확인, `.env` 작성(`OPENROUTER_API_KEY`, `DATABASE_URL`, `ADMIN_PASSWORD`)
- Supabase 프로젝트 확인(6장 실습 것 재사용), 비공개 깃허브 저장소, Streamlit 계정
- 완료 기준: `.env`가 `.gitignore`에 걸러지고, 키가 있는지만 "있음/없음"으로 확인된다.

### 1단계: 규칙 모듈 (`rules.py`) + 테스트 [1~2일차]
- 상수: 역할 6개, 정원 2~4
- `can_fill(student, role)`: 주·보조 역할 포함 여부
- `filled_required(members)`: 기획자·웹 프로그래머를 서로 다른 사람으로 채운 수(이분 매칭)
- `check_apply(team_members, applicant)`: 팀 꽉 참, 주 역할 중복, 필수 역할 자리 부족 판정 → 막힘 이유
- `validate_final(teams)`: 인원, 주 역할 중복, 필수 역할 충족 위반 목록
- 테스트: 공고 3장의 필수 역할 자리 계산 예 두 개, 부록 어려움 11단계
- 완료 기준: 단위 테스트 통과

### 2단계: DB와 로그인 [2~3일차]
- `schema.sql` 작성(유일성·check 제약 포함), Supabase에 적용
- `db.py`: 연결 한 번 생성(`st.cache_resource`), 죽은 연결 감지 후 재연결
- `auth.py`: bcrypt, 관리자 시드(앱 시작 때 생성·비밀번호 갱신), 로그인 화면(`login_*` key)
- 명단 업로드: `utf-8-sig` CSV 파싱, 검증, 초기화(`admin_*` key)
- 완료 기준: 쉬움.csv 업로드 후 학생·관리자 로그인, 틀린 비밀번호 거부, 학생의 관리자 기능 차단

### 3단계: 지원·투표·마감 [3~5일차]
- 화면: 팀 목록(`team_N`), 지원(`apply_N`), 찬성/거부(`vote_*`), 결과 안내(`result`), 내 팀 표시
- `service.py`: 지원 접수/막힘, 투표 기록(변경 불가), 거부 즉시 거절, 전원 찬성 시 **승인 직전 재검사** 후 승인 또는 거절, 투표가 끝난 순서로 처리
- 동시성: `(team_id, slot_no)`·`student_id` 유일 제약 충돌 시 먼저 온 학생만 기록
- 마감: 대기 지원 거절, 1명 팀 해체, `unassigned` 표시
- `st.fragment(run_every=5)`로 팀 목록과 투표 영역 자동 갱신
- 완료 기준: 연습용 쉬움 1~5단계, 중간 1~10단계, 어려움 1~14단계의 결과 첫 단어가 기대와 같다.

### 4단계: AI 배정 [5~7일차]
- `assign.py`
  - 프롬프트: 현재 팀 구성, 미배정 학생과 역할, 규칙 → JSON만 출력하게 요청
  - 3단 폴백: 호출 함수에 벽시계 120초 제한(스레드 또는 스트리밍으로 전체 시간을 잼), 429·빈 응답·JSON 오류·검사 불통과는 다음 모델로
  - 응답 길이 한도: `reasoning effort=low`, `max_tokens` 넉넉히
  - 검사 5가지(`rules.validate_final` 재사용)
  - 직접 배정: 백트래킹으로 모든 경우를 따져 검사를 통과하는 배정을 찾음. 없으면 이유를 계산
  - 사전 판정: 규칙을 지키는 배정이 없으면 AI를 부르지 않음
  - `assign_status`: "1차 모델 응답 대기 중…" 등 차수와 실패 이유 표시
  - `tf_ai_logs`에 호출 결과 기록
- 확정: `admin_confirm`으로 DB 저장, 새 브라우저에서도 유지
- 시험: 모델 호출을 가짜(mock)로 바꿔 시간 초과, 빈 응답, 위반 배정을 재현한다. 실제 호출은 한도 때문에 최소로 쓴다.
- 완료 기준: 3시나리오 모두 배정·확정까지 통과, 규칙 위반 배정이 걸러지는 화면 확보

### 5단계: 배포 [8~9일차]
- 비공개 저장소 연결(Streamlit Private access), Branch `main`, Main file path 확인
- Secrets에 세 값 등록, 배포 후 Sharing을 "public and searchable"로 변경
- 시크릿 창으로 로그인 화면 확인, 배포본에서 3시나리오 재확인
- 완료 기준: 시크릿 창에서 로그인 화면이 보이고 시나리오가 통과한다.

### 6단계: 마무리 [10~11일차]
- DB 일시정지 방지: 외부 예약 서비스(예: GitHub Actions의 일 1회 DB 질의)를 시도하고, 어려우면 11/2에 배포 앱을 직접 사용한다.
- README.md(공고 7.1절 양식): 배포 주소, 문서 위치, 고른 해결 방법, 쓴 모델 3개, **AI 실패 사례 1건+화면**, **클로드의 잘못된 답 1건+근거**, **내 앱의 문제점 1건+시나리오 단계·화면**
- 보안 점검: 키·비밀번호가 코드·커밋 기록에 없는지, 화면 출력이 없는지, 실제 사람 이름이 없는지
- 저장소 zip 만들기(`학번.zip`, `.env` 제외 확인), e-class 제출
- 11/2 마감 전에 제출하고, 마감 뒤에는 커밋하지 않는다(-5점).
- 11/3 09:00 전에 저장소를 공개로 바꾼다.
