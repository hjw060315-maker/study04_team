# PRD: 팀 편성 웹 앱

## 1. 목적
학생이 팀 프로젝트용 팀을 스스로 편성하고, 마감 뒤 팀이 없는 학생은 AI가 돕고, 앱이 AI의 답을 규칙으로 검사해 확정하는 웹 앱이다. 출처는 `중간과제 공고.pdf`이며, 아래 "공고 N.N절"은 그 절을 가리킨다.

## 2. 목표와 비목표
- 목표: 공고의 규칙(공고 2.3~2.5절)을 모두 지키는 앱, 공고 2.7절의 화면 key 준수, 쉬움·중간·어려움 시나리오 통과
- 비목표: 구글 로그인(`st.login`), 학생의 역할 변경, 실제 학생 정보 사용, 실시간 채팅

## 3. 사용자
| 사용자 | 권한 |
|---|---|
| 학생 | 학번+비밀번호(1234) 로그인, 팀과 팀원·역할 조회, 지원, 내 팀 지원에 찬성/거부 |
| 관리자 | 학번 `admin` 로그인, 명단 CSV 업로드와 팀 수 지정으로 초기화, 모집 마감, AI 배정, 배정 확정 |

관리자 계정은 앱 시작 때 `ADMIN_PASSWORD`로 만들거나 비밀번호를 갱신한다. 명단을 다시 올려도 관리자 계정은 남긴다. 학생 계정으로 관리자 기능을 쓸 수 없어야 한다.

## 4. 도메인 규칙
역할 6개: 기획자(PL), 웹 프로그래머(WP), 프론트엔드 디자이너(FD), 테스터(TT), 보고서 작성자(RW), 발표자(PT). 학생마다 주 역할 1개, 보조 역할 0~2개(CSV로 고정).

### 4.1 팀 규칙
1. 확정된 팀 구성에서 모든 팀은 2~4명이다(빈 팀 없음).
2. 한 팀에 주 역할이 같은 학생이 2명 이상이면 안 된다.
3. 모든 팀에 기획자를 맡을 학생과 웹 프로그래머를 맡을 학생이 **서로 다른 사람**으로 1명씩 있어야 한다. 주·보조 역할 모두 인정한다.

### 4.2 지원과 투표
| 상황 | 결과 |
|---|---|
| 빈 팀에 지원 | 투표할 팀원이 없으므로 바로 승인 |
| 팀원이 있는 팀에 지원 | 대기. 투표 시점의 팀원 전원이 투표 |
| 모든 팀원이 찬성 | 승인 직전에 규칙을 다시 검사하고 통과하면 승인, 위반이면 거절 |
| 한 명이라도 거부 | 즉시 거절 |
| 아직 투표 안 한 팀원이 있음 | 대기 |

지원 단계에서 **막힘**(접수하지 않음, 결과 안내가 "막힘: 이유"):
- 팀이 꽉 참(4명)
- 같은 주 역할의 팀원이 있음
- 이미 팀이 있음, 또는 결과를 기다리는 지원이 있음
- 모집이 마감됨
- 필수 포함 역할을 채울 자리가 모자라게 됨(공고 3장 어려운 해결)

**거절**은 접수된 대기 지원이 거부, 승인 직전 검사, 모집 마감으로 떨어진 것이다. 한 번 한 투표는 바꿀 수 없다.

필수 포함 역할 자리 계산: 지원자가 들어간 뒤 남는 자리 수가, 그 팀에서 아직 채우지 못한 필수 역할 수보다 적으면 막는다. 기획자와 웹 프로그래머는 서로 다른 학생이 맡아야 하므로, 한 학생이 둘 다 할 수 있어도 하나로만 센다(이분 매칭으로 채운 수를 구함).

### 4.3 마감과 배정
1. 관리자가 "모집 마감"을 누르면 지원·투표가 막힌다.
2. 대기 중인 지원은 모두 거절하고, 1명뿐인 팀의 학생은 팀에서 빠져 "팀이 없는 학생"이 된다.
3. 관리자가 "AI 배정"을 누르면 팀이 없는 학생만 팀에 넣는 배정안을 AI에게 받는다. 이미 팀에 있는 학생은 옮기지 않는다.
4. 배정안 검사 5가지: 미배정 학생 빠짐없이 배정, 한 학생은 한 팀에만, 모든 팀 2~4명, 팀 안 주 역할 중복 없음, 필수 포함 역할 충족.
5. AI 실패(무응답, 빈 응답, 오류, 검사 불통과) 때 2차, 3차 모델로 넘어간다. 모델마다 120초 전체 대기 시간 제한을 둔다.
6. 3차까지 실패하면 앱이 모든 경우를 따져 5가지 검사를 통과하는 배정을 직접 찾는다.
7. 검사를 통과한 배정안만 관리자에게 보여 주고, 확정하면 DB에 저장한다.
8. 규칙을 지키는 배정이 없으면 배정안을 만들지 않고 "규칙을 지키는 배정이 없음"과 이유를 보여 준다(이때 AI는 부르지 않는다).

## 5. 기능 요구사항
### 5.1 명단 올리기 (관리자)
- CSV(UTF-8, BOM 가능, `utf-8-sig`)와 팀 수를 받아 지원·투표·팀원·마감 표시를 지우고, 학생과 빈 팀(팀1, 팀2, …)을 만든다.
- 형식: `student_no,name,main_role,sub_roles` (보조 역할은 `;` 구분, 없으면 빈칸). 잘못된 역할 값은 거부한다.
- 학생 비밀번호는 모두 `1234`이며 bcrypt 해시로 저장한다.

### 5.2 학생 화면
- 로그인한 사람 표시, 팀 목록과 팀원(이름, 주 역할, 보조 역할), 내 팀 표시("내 팀"), 팀이 없으면 "아직 팀이 없음".
- 이미 팀이 있음, 결과 대기 중인 지원이 있음, 마감됨이면 지원 단추를 숨기거나 비활성화한다.
- 내 팀에 들어온 대기 지원마다 찬성/거부 단추. 투표한 지원은 단추를 숨기고 "내 투표: 찬성"을 보여 준다.
- 다른 사람의 변경을 `st.fragment(run_every=5)`로 5초마다 자동 갱신한다(어려운 해결).

### 5.3 관리자 화면
명단 업로드, 팀 수, 처음 상태 만들기, 모집 마감, 팀이 없는 학생 표시, AI 배정, 배정 진행 안내, 배정안 확정. 모든 관리자 단추의 결과는 "승인:" 또는 "막힘:"으로 시작한다.

### 5.4 화면 key (공고 2.7절, 그대로 지킴)
`login_student_no`, `login_password`, `login_submit`, `whoami`, `result`, `team_N`, `apply_N`, `vote_yes_{학번}`, `vote_no_{학번}`, `admin_roster_file`, `admin_team_count`, `admin_start`, `admin_close`, `unassigned`, `admin_assign`, `assign_status`, `admin_confirm`. key에는 영문, 숫자, 밑줄만 쓴다. `result` 안내는 "승인", "대기", "거절", "막힘" 중 하나로 시작한다.

## 6. 해결 방법 선택 (공고 3장)
점수를 최대로 받기 위해 어려운 해결을 기본 목표로 한다.

| 기능 | 선택 | 근거 |
|---|---|---|
| 다른 사람의 변경 보기 | 어려운: `st.fragment` 5초 갱신 | 1점 |
| 필수 포함 역할을 지킬 수 없는 팀 | 어려운: 지원 단계에서 막음 | 7점 |
| 같은 팀 대기 지원이 여럿 | 어려운: 승인 직전 재검사, 투표가 끝난 순서로 처리 | 3점 |
| 마지막 자리에 두 명 동시 | 어려운: DB 유일성 제약, 충돌 시 먼저 온 학생만 기록 | 0.5점 |
| AI 응답이 늦을 때 | 어려운: 모델마다 전체 120초 벽시계 제한 | 1점 |
| 3차 모델까지 실패 | 어려운: 완전 탐색(백트래킹)으로 직접 배정 | 최대 6.5점 |
| AI 대기 중 화면 | 어려운: 몇 차 모델 대기 중인지 표시 | 1점 |
| DB 일시정지 방지 | 어려운: 외부 예약 서비스로 매일 DB 질의. 시간이 부족하면 쉬운 해결(11/2 사용)로 대체 | 0.5점 |

## 7. 비기능 요구사항
- **키 관리**: `OPENROUTER_API_KEY`, `DATABASE_URL`, `ADMIN_PASSWORD`는 로컬 `.env`, 배포는 Streamlit Secrets. 코드, 커밋, 화면에 값을 출력하지 않는다.
- **DB**: Supabase(Postgres), 모든 테이블 이름은 `tf_`로 시작. 연결은 한 번만 만들어 재사용(`st.cache_resource`), 끊기면 재연결한다.
- **보안**: 비밀번호 bcrypt 해시, 학생의 관리자 기능 접근 차단, 틀린 비밀번호는 로그인 거부.
- **AI**: OpenRouter 무료 텍스트 모델 3개(1·2·3차). `openrouter/free`는 쓰지 않는다. `reasoning effort=low`, 넉넉한 `max_tokens`. 빈 응답도 실패로 처리한다. 무료 한도(하루 50회, 분당 20회)를 아끼기 위해 배정 불가능이 확실하면 AI를 부르지 않는다.
- **시각**: 배포 서버는 UTC이므로 화면에는 한국 시각으로 변환한다.
- **정직성**: 연습용 시나리오의 이름·순서를 보고 결과를 미리 정하는 코드를 쓰지 않는다. 실제 사람 이름·학번을 쓰지 않는다.

## 9. 인수 기준
1. 공고 부록의 쉬움·중간·어려움 연습용 시나리오가 단계마다 기대 결과와 같은 첫 단어를 보인다.
2. 최종 확정한 팀 구성이 4.1의 세 규칙을 모두 지킨다(새 브라우저로 열어도 유지됨).
3. 모델 1차가 120초를 넘기거나 실패하면 2차, 3차, 직접 배정 순으로 넘어가며 이 기록이 남는다.
4. 학생 계정으로 관리자 화면에 접근할 수 없다. 틀린 비밀번호로 로그인되지 않는다.
5. 키와 비밀번호가 저장소 어디에도 없다. `schema.sql`이 실제 DB와 같다.
6. 시크릿 창에서 배포 주소를 열면 로그인 화면이 보인다.
